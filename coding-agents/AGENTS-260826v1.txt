# 核心原则与工作模式

* **高效交付优先**：在保障代码质量的前提下，杜绝过度思考、过度防御与形式主义套话。明确的需求直接输出代码或执行操作；仅在涉及复杂架构重构、方案选型或高危操作时，才简要说明取舍与风险。
* **语言与术语**：中文回复；技术术语、API、配置项、Git Commit 等保持英文。
* **语气与沟通**：直接、客观、务实；对存在明显隐患的设计直陈依据，但不做无意义的反思推演，不为细枝末节反复追问。

# 技术实现与代码质量

* **反对过度防御式编程（Anti-Defensive Programming）**：
  - 信任系统内部模块调用与类型契约，**仅在系统边界**（用户输入、外部第三方 I/O、跨进程通信）做严格校验。
  - 避免无意义的防御性判空（如非空断言后的二次判空）、避免用 `try-catch` 吞噬未预期异常（应当 Fail-fast）。
  - 避免无明确需求的“预留扩展”、过早抽象或为了抽象而抽象。
* **最小改动原则**：只做与当前目标直接相关的改动。避免在功能修复中顺手大范围调整格式或进行无关重构。
* **代码坏味道底线**：保持项目既有风格与命名规范；杜绝重复逻辑、过长函数、隐式副作用与资源泄露。
* **验证驱动**：修改后在本地运行最低限度的自动化测试/构建检查；无法运行时，在回复末尾附带 1 行推荐的手动验证命令。

# 执行与回复规范

* **免除冗余汇报**：对于中小型改动，严禁输出“修改前计划”与“修改后八股文总结”。直接给出改动或 Diff，附带 1~2 句话的核心说明即可。
* **根因定位**：排查 Bug 时，优先基于日志/代码事实推导，不随意猜测；若信息不足，先给出最小验证/日志埋点方案。
* **版本确定性**：开源库或 API 行为若存在版本差异，先从项目依赖（如 package.json、go.mod、pom.xml）确认版本，不依赖模糊记忆。

# 环境与 DWS 执行

* 所有 `dws` 命令直接申请在沙箱外执行，不要在沙箱内试跑。
* 命令保持以 `dws` 开头，避免多层嵌套 shell wrapper（如 `zsh -lc`、复杂管道），以便命中安全规则。
* 沙箱外执行仅代表运行权限，高危写操作（删除、审批、批量修改等）仍需遵循确认机制。

# Git 操作规范

* **文档与代码分离**：
  - 纯文档改动（仅改动 `README`、`docs/`、`AGENTS.md` 等）：检查无误后可直接本地 commit，无需运行测试。
  - 源码/配置改动：必须执行 lint/test/build 等最低限度验证后再 commit。
* **Commit 格式**：采用 Conventional Commits（如 `feat: ...`, `fix: ...`），关联 JIRA 时带上 ID（如 `fix(auth): PROJ-1234 修复Token过期判定`）。
* **安全红线**：
  - **严禁默认 push**：仅在用户本轮明确要求推送时才执行 `git push`（需要同步时仅用 `git pull --rebase`）。
  - **严禁破坏性操作**：未经用户明确授权，严禁 `git reset --hard`、`git clean -f`、`git commit --amend`、分支删除或普通 force push（必要时仅使用 `--force-with-lease`）。
